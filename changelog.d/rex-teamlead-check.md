### Added

- **`rex-team.sh check`: the lead runs the checks itself** (ADR 0017). A worker's `done` proves it stopped, never that its work is right; following andrebrov/agent-factory-lab experiment 10's validity rules ("never on another agent's word"), the lead now runs commands it chose, one `--run` each, in the developer's worktree after the `candidate` gate. Nothing is read from the worker's report. The command refuses with `check_mismatch` unless the writer's branch tip and the worktree `HEAD` are the candidate, and with `check_dirty` when the worktree has uncommitted or untracked changes, before running anything. Both clean-tree reads compare content, not `git status`: the candidate's tree is read into a temporary index in the checkout's own git directory, which git never lists as worktree content whatever `TMPDIR` says, and the working tree is staged into it with `git add -A`, so every tracked and untracked, non-ignored file is hashed through the repository's clean filters and `core.autocrlf`, then diffed against `HEAD`. The real index, its cached stat data and its assume-unchanged and skip-worktree flags are never read or written, so neither a same-size rewrite with its mtime restored in the same ctime second, nor a dangling symlink or other change under skip-worktree, nor a hiding `status.showUntrackedFiles` or `core.fsmonitor` setting records a false `pass`, and clean content under those flags is accepted. `core.fileMode=true` is forced so an executable-bit change shows. An untracked nested repository, such as one a run `git init`s or clones, is a change named by its path. Paths ignored through `.gitignore`, `info/exclude` or `core.excludesFile` are exempt, so build output in them is not a change. Submodules and sparse checkouts are unsupported: a candidate whose tree holds a gitlink, or a sparse checkout, is refused with `check_unsupported` before any run, and the lead takes it to the operator instead of the developer. Hashing costs one `git add -A` per read, two per `check`: on this repository's 390 files, one read took about 0.09 s and `check --run true` about 0.22 s. Each command runs with `bash -c`, no stdin and a per-command timeout (default 1800 s) that kills its whole process group, its combined output written to `$REX_TEAM_HOME/<task>/checks/<role>-<k>/<i>.log`; stdout carries the log path, never the output. Exit 0 is `pass`, exit 1 `fail`, and any other exit, a timeout, a signal, exit 126 or 127 (reported as that exit status alone, since the command may have run before exiting with it), or a run that moved `HEAD` or left the tree dirty is `invalid`; a run that changed the worktree stops the remaining runs, which are reported as not run. The overall verdict is `invalid` over `fail` over `pass`, and the command exits 0 whenever its runs were classified. The latest check is recorded on the worker and shown by `status`, and the tab reads `· #<n> checks pass|fail|invalid`. Covered in `skills/rex-teamlead/tests/test_team.py` with real `git` and real `bash -c` commands: pass, fail, exit 2, 126, 127, a signal, a timeout, a command that commits, a command that leaves a file, each refusal in both directions, and the recorded state, plus one run through `python -m rexlead`.

### Changed

- **`skills/rex-teamlead` gates the reviewer on the lead's check.** New Step 8 runs `check` with the commands picked at Step 1: `pass` spawns the reviewer, `fail` sends the developer one correction brief with the log paths, and `invalid` goes to the operator and never enters the fix loop as a code defect. The later steps are renumbered. The reviewer brief names the passed checks, and the reviewer need not rerun the full suite. The Step 6 routing list and the Step 13 blocking-findings bullet are split into atomic bullets, folding in PR #84's last advisories.
- **The reviewer's verdict binds the Rex round; the operator alone approves a downgrade.** Step 13 routes on the reviewer's `verdict:` instead of the lead's own classification of the findings. `approve` proceeds to the release and `changes-requested` runs the fix loop. An `approve` that lists a `blocking` finding routes as `changes-requested`. The reviewer's classification of each finding binds too: the lead never reclassifies on its own, and a `blocking` finding it disagrees with is reclassified as advisory only on the operator's explicit approval, recorded in the PR body at release; without approval it stays blocking. `rules/review-severity.md` Two Tiers states this for every Rex team round, so the skill and the policy reviewer read the same rule.
- **The Rex team state record is `schema_version` 2.** It adds the optional worker `check` (`candidate`, `verdict`, `checked_at`). The owner upgrades a version-1 record on read and rewrites it; `skills/rex-teamlead/state-schema.md` documents the version handling.
