# Changelog

Every entry carries the motivation and worked examples stripped from the rule bodies
(`rules/context-artifacts.md` Writing Style). PRs add their entries as `changelog.d/`
fragments; the publish workflow writes each `## <version> — <date>` heading on merge
(`changelog.d/README.md`).

## 0.18.0 — 2026-10-22

### Changed

- **`herdr-teamlead` `SKILL.md` is now a step router; each step's detail loads only when the lead reaches it.** The lead loaded the whole 26 KB skill on every invocation, and `tessl plugin lint` warned about its size. `SKILL.md` keeps the 20 flat steps, the Step 1 mode gate and routing, and the command blocks no reference already carried; it drops to about 8.6 KB. The rest moved without changing its meaning: Steps 2–7 detail and command blocks into `references/round-setup.md`, which already carried most of them twice. Steps 8–10 moved into the new `references/round-dispatch.md`, the judge chain into `references/judge-round.md`, read only when a judge trigger fires, and Steps 18 and 20 into `references/round-completion.md`. Every bootstrap command block stays in a file the `rules/script-delegation.md` carve-out already covers, so the carve-out is unchanged. Adapted from upstream jbaruch/herdr-policy c2416d4a (#40).
- **`tests/test_skill_invocations.sh` follows the moved blocks.** It reads the carve-out's covered reference list from one array. It rejects a `$CP` bootstrap block in any other Herdr skill file, and it requires every `references/<file>.md` Step N pointer in `SKILL.md` to land on a real step heading. Both new guards are tested with a fixture they must reject and one they must accept.

## 0.17.1 — 2026-10-22

### Fixed

- **A no-work retry's own brief must name the recovered checkout, and a spent receipt no longer takes an old retry ID** (#62). `brief_identity` masks the report path, so a retry brief whose report path prefixes its checkout path could share the original brief's identity while naming a different, never-verified checkout. Both retry gates (`prepare` and the pre-reservation `recheck`) now require the retry brief's worktree field to resolve to the receipt's canonical checkout. Separately, a listed `not_sent` retry ID was checked only while its receipt was the task's open one. After another retry applied and was refused, re-applying the old ID passed, was saved, and left the ledger unreadable. The ID's own receipt is now checked whatever the latest applied dispatch is, in `recheck` and in `reserve`, before any save. Proven by two regressions in `skills/herdr-teamlead/tests/test_no_work_recovery.py` that failed on the prior code.

## 0.17.0 — 2026-10-22

### Changed

- **Recovery store version 10 adds `no_work_recoveries`**. The owner migrates a version-9 store by adding the empty collection, and refuses a version-9 store that already carries it. The schema is in `skills/herdr-teamlead/state-schema.md` Recovery records, and the decision is ADR 0011 (`docs/adr/0011-no-work-recovery.md`).

### Fixed

- **A closed no-work initial developer assignment can be retried once through `teamlead recover-no-work`**. `skills/herdr-teamlead/references/team-operation.md` Stalled Workers calls a clean, unchanged stall a `not_sent`-equivalent that may be retried, but the owner refused a second initial assignment and the only way forward spent fix 1. The new owner command takes the saved `wait-report.sh --worktree --base` JSON. It verifies the stall against the dispatch's enrolled worker, report and task base, and requires the stalled checkout to resolve to the one worktree the developer brief's worktree field names. It then rechecks live state: the pane is gone, the enrollment is resolved, the report is absent, and the checkout is clean at the base. It then writes a receipt. `plan` and `apply` admit one fresh initial assignment of the unchanged brief, with a fresh, unoccupied report path and a fresh context. A dry run of the retry runs the static checks and contacts no Herdr. `apply` repeats every live check before any input and again immediately before reservation, so a report that lands late refuses the retry, and binds the retry to the receipt in the reservation save. The receipt keeps the checkout's canonical real path, and each retry gate first requires the brief's worktree to still resolve to it. A recovered refusal move no longer counts as the outstanding move, so the retry goes to a provider that has not refused that brief. A recovered operator-authorized dispatch passes its authorization, with its provider and brief limits, to its retry, and the retry must use a fresh dispatch ID so an older `not_sent` row cannot be bound and leave the store unreadable. The original row and the correction count are unchanged, and replay grants nothing more. Proven through `teamlead.sh` with a real git checkout and a real `wait-report.sh` run in `skills/herdr-teamlead/tests/test_no_work_recovery.py`. The test failed on the prior code with `invalid choice: 'recover-no-work'` and the initial slot refused. Adapted from upstream jbaruch/coding-policy 45f98ac2 (#763).

## 0.16.1 — 2026-10-22

### Fixed

- **A new plugin's first release can capture its registry baseline.** The versions API answers a plugin with no versions with a structured `{"error":{"status":404,"title":"Not Found"}}` body and `tessl api` exits 1. `registry-version.sh` treated that as a tool failure, and `capture-registry-baseline.sh` parsed `tessl plugin info`, which answers the same case with prose and exit 1. Either way the release stopped before its first merge. `registry-version.sh` now classifies that exact body (top level holds only `error`; `error` holds only `status`/`title`/`message`; numeric 404; title `Not Found`) as never published only when `tessl` exits 1 for it, the status the CLI returns for that answer. The same body with any other status (0, 2, 126, a 137 kill) is a failure. Any other 404 shape, a 401, a 5xx, a transport failure or an unparseable body still fails.
- **`capture-registry-baseline.sh` reads the versions API and can emit `unpublished`.** It sources `registry-version.sh` instead of parsing `tessl plugin info`, and prints `{"version":"unpublished"}` for a verified never-published plugin. It never prints an empty or guessed baseline.
- **`verify-publish-landed.sh` accepts the `unpublished` baseline.** From it, conjunct 2 requires the registry to show any published version: a still-absent plugin after a successful run is exit 1 (did not land), never a vacuous pass. A baseline that is neither numeric `MAJOR.MINOR.PATCH` nor `unpublished` (a stray `null` from `jq -r`, a prerelease) is now an argument error, exit 2. `skills/release/SKILL.md` Step 7 names the sentinel.
- **`registry-version.sh` rejects malformed version entries.** It used to drop entries whose `.attributes.version` was missing or null, and it ignored the extraction's exit status. So `{"data":[{"attributes":{}}]}`, a numeric `"version":123` or a non-object entry read as never published, and capture turned that into `unpublished`. Now every `.data` entry must carry a numeric `MAJOR.MINOR.PATCH` version string, or the read exits 2. That covers an empty string, `1.2`, `v1.2.3` and a prerelease such as `1.2.3-rc1`, alone or hidden behind a valid version that sorts later. Prereleases are rejected because this plugin family never publishes them. A failed extraction also exits 2. Only an empty `.data` array or the exit-1 not-found body yields an empty result.
- **Step 7 guards every script-to-jq handoff.** `PRE=$(capture-registry-baseline.sh ... | jq -r .version)` reported jq's status, and jq accepts empty input, so a failed capture yielded an empty `PRE` with exit 0. The baseline capture and both `resolve-publish-run.sh` calls now capture the script's JSON in a guarded assignment, then parse it with a guarded `jq -e` that requires a string `.version` or a numeric `.database_id`. Never substitute an empty or guessed baseline such as `0.0.0`.
- Proven with a fake `tessl` (and `gh`) on PATH: the structured 404 is accepted, the reject cases still exit 2, and the first-publish landed check passes, fails on a still-absent plugin, and fails on a failed run. The accept cases fail on the previous scripts.
- Adapted from upstream jbaruch/coding-policy 6bc2d0f4.

## 0.15.0 — 2026-10-15

### Added

- **Configurable judgment pins: `top_models` in config.json.** An optional top-level `{kind: [model id, ...]}` block extends the built-in `TOP_MODELS` per kind, never replacing it. Validation is strict (known kinds, non-empty arrays of distinct model ids); an id already built in is accepted so a later built-in addition never breaks a config. The effective pins reach tier parsing, `select_tier`'s high-risk top-model switch, and the `judge` check. The block needs config schema 4; schemas 1 to 3 stay readable unchanged, and one carrying `top_models` is refused with the instruction to set `schema_version` 4 (the operator owns that bump; the Codex policy reviewer asked for an explicit version instead of a silent shape change). Decision recorded in `docs/adr/0009-configurable-top-model-pins.md`. Fixes #47, where a 0.7.10 config broke on upgrade because the frozen allowlist lagged the CLIs.

### Changed

- **`rules/stateful-artifacts.md`: operator-authored configuration exception.** Migration Policy gains a narrow exception, with seven atomic preconditions, for a file no skill writes: the owner reads every documented version and upgrades in memory only, refuses a version-gated field in an older file with the version to set, and its schema doc lists the gates. The Codex policy reviewer flagged that the config's 1-3 to 4 bump had no owner migration; the coordinator chose not to let teamlead rewrite the operator's config, so the rule names the alternative instead. herdr-teamlead's `config.json` takes it: `state-schema.md` cites it with the gate table (`tiers` 2, `capabilities` 3, `top_models` 4; `launch_args` ungated, correcting the doc that said schema 2 added it), and the `tiers` and `capabilities` refusals now name the file, the agent index and `set "schema_version" to N`.

- **Built-in pins track the current CLIs.** Codex adds `gpt-6-astra` and `gpt-6.1-sol`; Claude adds `opus-5-5` and `claude-fable-5-1` (`claude-opus-5-5` was already pinned). Superseded ids stay.
- **Codex accepts `max` and `ultra` effort.** codex-cli 0.160.0 lists `low, medium, high, xhigh, max, ultra` as `supported_reasoning_levels` for `gpt-6.1-sol`, `gpt-6-astra` and `gpt-5.6-sol` (`~/.codex/models_cache.json`); `codex exec --help` documents no effort enum. Risk escalation no longer lowers a `max` or `ultra` row to `xhigh`.
- **The judge block meets the judgment floor.** When the judge's agent is configured, its model must be a pin of that agent's kind (`top_models` included) at high effort or above; `preflight` now checks the judge before any worker contact. A judge on an unpinned model, previously accepted silently, is refused with the `top_models` fix named. A configured judge agent whose kind has no pins or effort floor is refused instead of passing silently; a judge naming an undeclared agent is still left to the planner. Test fixtures that pinned the judge to retired ids (`claude-opus-4-6`, `grok-4`) move to current pins.

### Fixed

- **`start-judge`'s config is part of its contract.** `start-judge` compares the plan against the current config, but neither `start-judge-worker.sh` nor SKILL.md Step 14 named `--config`, so a round planned on a non-default config was compared against the default one (Codex policy review on PR #54). The launcher header and usage now carry `[--config FILE]` (forwarded to `teamlead.sh`, which already accepted it) and refuse a `--config` without a path; SKILL.md's preflight, measure, plan, start-judge and apply blocks, `references/round-setup.md`, and the retrospective and recovery command notes pass the round's same `--config`.
- **A non-string agent `kind` is a config error, not a crash.** A list or object `kind` reached the top-model lookup and raised `TypeError` with a traceback, bypassing the structured error (Copilot on PR #54). `validate_config_schema` now refuses it before any pin lookup, for every reader.
- **Every config.json reader checks the schema first.** `parse_judge` and `parse_role_costs` skipped `parse_config`'s readable-version check, so a schema 5 config's `judge` and `role_costs` were consumed (Codex policy review on PR #54). Schema and field-gate validation now live in one function, `validate_config_schema`, which all three readers (and their `load_*` loaders) run before reading a field; a newer, older-unreadable or missing version and an under-versioned gated field are refused. The `top_models` guard is also exercised through the real `teamlead.sh plan` entry point (`tests/test_top_models_cli.py`).
- **Retained fixes rank effort on the shared order.** `assign.py` kept a private rank table ending at `max`, so a verified `ultra` session was refused an `ultra` retained fix and a `high` or `xhigh` session silently continued below a requested `ultra` (found by Copilot on PR #54). The check is now `retained_developer_tier`, ranking on `tiers.EFFORT_ORDER`; no other private effort table exists.
- **A refused judgment row says what to change.** The error names the agent, the round, the refused model and effort, the accepted models and efforts for that kind, and `top_models.<kind>` in config.json, with the same facts in the error details.
- **`start-judge` checks the plan against the current config.** It used to trust the plan's tier and the caller's `--kind`, validating the pair only as a non-judgment build row. It now loads the current config before any Herdr contact and refuses a plan whose judge agent, model, effort, kind or normalized `launch_args` differs from the configured judge block and its agent, or whose pair misses the effective judgment floor, then launches from the current config's `launch_args`. Refusing on a launch-option mismatch, instead of silently launching the current value, keeps the plan the audited record of what started, the same rule as for model and effort; the Codex policy review on PR #54 found launch_args had been left out. Audit of every plan field start-judge reads: judge `agent`, `model`, `effort` and `launch_args` are verified against the current config; `kind` comes from `--kind` and is verified against the agent's configured kind; `mode` and `task_context.task` are plan decisions checked against the flags, not config fields.
- **An explicit `"top_models": null` is refused.** It read as an omitted block; it is now refused as a non-object like any other malformed value, through the `teamlead.sh plan` entry point as well.
- **Step 13 and Step 14 name the right inputs.** Their placeholders pointed two steps ahead (`<step-14-measure-output>`, `<step-15-plan-file>`); they now read `<step-12-measure-output>` and `<step-13-plan-file>`, the steps that produce them.

## 0.14.0 — 2026-10-15

### Added

- **`hooks/session-start.sh`: one SessionStart hook that delivers every status.** Probed on tessl 0.115.0 with a throwaway fixture plugin under `$TMPDIR`: `tessl hook run` keeps only the LAST hook's output in a SessionStart group (also across groups), and the hook sees `TESSL_AGENT` and `TESSL_PLUGIN_DIR` but not `HERDR_ENV` or any other session variable. Our group ended with `beans-prime`, silent outside a beans repo, so Claude Code sessions received `{}`: no sync, version, or team status, and worker detection never saw `HERDR_ENV`. A scratch-project install of the old tree returned `{}` with `main` one commit behind; the new tree's native entry returned the merged statuses. The aggregator runs the hooks listed in `hooks/session-start-hooks.txt`, merges their `additionalContext`, and reports a failing or malformed child as its own status line. It is declared under `nativeHooks.claude-code` (single-string command, the session's environment intact) and stays the only portable SessionStart hook for other agents, where it exports `SESSION_START_MODE=portable`; the portable run defers when `TESSL_AGENT=claude-code`. The Codex adapter reads the same list for its allowlist, so the Codex plugin's separate handlers are unchanged. Without jq the children still run and the payload is one fixed status naming the jq install step; the aggregator never calls python3, so it needs no Direct Python Carve-Out entry. The decision, payload contract, shared list, portable-mode behavior, and compatibility are recorded in `docs/adr/0006-native-aggregating-session-start.md`. Idea from upstream jbaruch/coding-policy 73fbcb5 and 0.3.278.

### Changed

- **`check-git-sync` fast-forwards instead of only reporting** when the session is a proven non-worker in native mode, the default branch is checked out with no tracked changes, and a fresh fetch shows it strictly behind; `git merge --ff-only` refuses everything else. Off-default, dirty, diverged, portable, and unverified sessions are still reported, and `rules/sync-before-work.md` now says so: a standalone agent or a Herdr lead syncs any drift the hook reports, and a Herdr worker only reports it (`rules/agent-team-operation.md` Workers). Idea from upstream 0.3.275. Upstream also fast-forwards a default branch that is not checked out (`fetch . origin/<b>:<b>`); not adopted, so the hook never moves a branch the session is not on.
- **`check-policy-freshness` is kept, not removed.** Upstream removed its counterpart as a duplicate of `check-tessl-latest`. Ours is not one: `check-tessl-latest` returns before `tessl update` in a project with no `gamussa/*` dependency and never reports other plugins, while `tessl outdated --json` reports every plugin in the project, third-party pins included (verified in a consumer pinning `jbaruch/blog-writer` 1.1.42 against 1.1.50). Removing it would leave those pins with no renewal signal (`rules/dependency-management.md` Freshness).
- **`rules/script-delegation.md`: narrow exception for `hooks/bounded-run.sh` transparent deadline-wrapper stdout.** The runner passes its command's stdout and stderr through unmodified, so it cannot also emit JSON; its own diagnostics go to stderr only, and its exit codes (the command's, 124, 125) are documented and tested, now including stderr pass-through. Raised by the Codex policy review on PR #52.
- **`rules/testing-standards.md` Determinism: narrow exception for elapsed-time bounds in tests of code that enforces a deadline.** A fake clock cannot prove that real processes are stopped, so such a test may assert an upper bound on elapsed time only: a named constant at least 4x the deadline under test plus fixed slack, with no exact duration, lower bound, ordering, or date input, and a deterministic outcome preferred wherever one exists. Raised by the Codex policy review on PR #52.
- **The Codex adapter tolerates EPERM from a process group.** macOS answers `killpg` with EPERM while a group's members cannot take a signal yet (a child between fork and exec) or only unreaped zombies remain; the adapter read that as a fatal error and reported `cannot load policy context` instead of the timeout. It now counts EPERM as a present group and keeps polling to the SIGKILL. A test refusing the first group signal fails on the old adapter with that exact message; the suite's own liveness probes accept EPERM for zombies. Found as a CPU-load flake in the PR #52 test run.
- **Liveness never comes from `kill -0`.** `bounded-run.sh` read every `kill -0` failure as "gone", so an EPERM probe (macOS, a member mid-exec) let the runner wait on a running leader past its deadline. Leader and group liveness now come from `ps` alone (`ps -p` exit 1 is the only "gone"); an unreadable state counts as running. A test exporting a `kill` that refuses every `-0` probe got exit 0 from the old runner and 124 now.
- **`check-git-sync` surfaces a repository git cannot read.** Only exit 128 with "not a git repository" (read under `LC_ALL=C`) is the silent non-repo case; any other `rev-parse` failure, such as a broken `.git/config` or dubious ownership, now warns on stderr instead of passing as a no-op. Raised by the policy reviewer on PR #52.

### Fixed

- **`check-git-sync` never runs repo code, never fetches from a worker, and never loses local data.** Every git call that can update refs, the index, or the work tree carries `-c core.hooksPath=/dev/null`: the fetch (`reference-transaction`), the `git status` check (an index refresh runs `post-index-change`), and the fast-forward merge (`post-merge`). The Herdr role is decided before the throttle stamp and the fetch: a worker reports drift as last fetched, and a session whose role cannot be proven (a failed probe with `HERDR_ENV` set, or a linked worktree in portable mode) neither fetches nor fast-forwards. The merge passes `--no-overwrite-ignore`, so a path origin starts tracking that holds ignored local data refuses the fast-forward instead of overwriting it. Each guard has a case that fails with that guard reverted. Ideas from upstream 7e436ae, 89393f0 and 0.3.278; the status hook and the ignored-file overwrite were raised by Copilot on PR #52.
- **`check-git-sync` runs no command from repo-local config.** Every git call now goes through one helper adding `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c gc.auto=0 -c maintenance.auto=false`, so a repo-configured `core.fsmonitor` program never runs on the status check or the merge, and fetch and merge start no background gc. A filter driver (`filter.<name>.clean/smudge/process`) defined in repo-local config refuses the fast-forward with a report: a checkout would run it, and git has no switch that disables filters without changing the checked-out bytes. Reviewed and left as configured: merge drivers and `diff.external` (neither runs in `merge --ff-only` or `status --porcelain`), and the fetch transport (credential helpers, a custom ssh, `core.gitProxy`, `uploadpack`), which is how this remote is reached and runs identically under the hand-run `git fetch` the sync rule requires; disabling credential helpers would break authenticated fetches. The filter lookup reads repository config through its includes and the per-worktree config (`--includes --show-scope`, scopes `local` and `worktree`); a filter in the user's own global or system config stays trusted and does not block. An fsmonitor case, a local-filter case, an included-filter case and a worktree-config filter case each ran their program on the old hook and do not now. Raised by Copilot on PR #52.
- **Session-start work has hard deadlines without `timeout`.** New `hooks/bounded-run.sh` runs a command in its own process group (bash job control, no python3) and returns its exit code once the whole group has exited, or stops the group (SIGTERM, a 2s grace, SIGKILL; liveness checked on the group, not the leader) and returns 124 at the deadline, even when the leader already exited 0. A runner stopped from outside stops and reaps its own group within a 1s grace, so nested runners never leave a process holding stdout.
  - `check-git-sync` always runs its fetch through it at `SYNC_FETCH_TIMEOUT`; git's `http.lowSpeedLimit`/`http.lowSpeedTime` and ssh `ConnectTimeout`/`ServerAlive*` (plain default `ssh` only) end most stalls sooner. An ssh that connects and then never answers is killed at the deadline.
  - `session-start.sh` runs each child through it (45s each, 120s total), reports a stopped or never-started child as its own line, keeps every other status, and exports the child's deadline as `SESSION_START_CHILD_DEADLINE_SEC`; `check-git-sync` caps its fetch at two thirds of it, so the inner deadline fires first.
  - `hooks/codex-session-start.py` exports the same variable, and on timeout sends SIGTERM, waits up to 3s for the whole group, sends SIGKILL, and drains output for at most 2s, instead of a SIGKILL that skipped the runner's trap followed by an unbounded drain.
  - Group liveness skips defunct members: `kill -0` alone counts a zombie on Linux, so under a non-reaping parent an exited orphan held the group open and a hook that exited 3 came back as 124. The runner now reads states with `ps -A -o pgid= -o stat=` (macOS and procps alike) and ignores `Z`; when `ps` cannot answer, every member counts as running, so the deadline still holds. A fake-`ps` case on the liveness helper failed first on both shells; an end-to-end case with a real unreaped zombie in the group passes on macOS (whose `kill -0` already skips zombies) and is the Linux regression in CI.
  - Raised across Copilot's reviews on PR #52. The escalation, nested-runner, early-leader-exit, deadline-cap, stalled-child and adapter cases each fail with their fix reverted, on bash 3.2 and 5.3.
- **The aggregate keeps agent instructions out of the relayed status block.** `session-start.sh` appended every child's `additionalContext` into one run, so the beans guide, which is deliberately not a status, read as a continuation of the `Session-start status — ` block the agent relays verbatim (`rules/hook-action-reporting.md`). Statuses now come first; each non-status payload follows under its own "Agent context, not a session-start status — do not relay it to the user (from <hook>):" header, in native and portable mode alike. `rules/hook-action-reporting.md` now names that header as the end of a payload's relayable status, with the text after it read and acted on but never relayed. A delimiter in `additionalContext` was chosen over a separate channel: a SessionStart hook has no agent-only field besides `additionalContext`, and `systemMessage` is shown to the user. A test requires the header the aggregator emits to appear verbatim in the rule and in ADR 0006, and fails when either side drifts. The Codex adapter runs each hook as its own handler and needed no change. A status-plus-guide case failed first in both modes. Raised by the Codex policy review on PR #52.
- **`check-git-sync` leaves a custom ssh command unchanged.** The OpenSSH `-o ConnectTimeout`/`ServerAlive*` options were appended to any configured ssh, so a `GIT_SSH_COMMAND` or `core.sshCommand` wrapper using the simple variant, which rejects extra arguments, failed every fetch. The options now go only to the plain default `ssh` (no `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_SSH_VARIANT`, `core.sshCommand` or `ssh.variant`); `bounded-run.sh` bounds every fetch either way. ## 0.7.8 — 2026-10-04

### Changed

Three testing directives borrowed from the incident log of [andrebrov/drover](https://github.com/andrebrov/drover) (`docs/LESSONS.md`, MIT), a bash toolkit that runs a Herdr agent fleet from a daemon. Its code and architecture were not adopted; only the lessons that coding-policy's rules did not already state.

- **A guard is tested in both directions** (`rules/testing-standards.md` Coverage). A new or changed shipped or CI check that decides pass or fail ships with one input it must reject and one it must accept; a test's own assertions are not guards, or the rule would recurse. A guard run only on the input it was written for may reject nothing, or everything. drover's log records a `printf | grep -q` guard under `pipefail` that rejected every input and idled 19 agents for about four hours, and a budget check that read an expired banner as live and refused over a hundred dispatches: both had been run only against the case they were written for. The onboard-repo preflight in #21, which can never pass its `codex-auth` check, is the same class here.
- **Tests that cannot fail** (`rules/testing-standards.md` Assertions). Four bullets: a test that never runs the code under test, or observes none of its outcomes, is documentation — a raised error, crash or timeout counts as an observed outcome, so a no-throw smoke test is a test; a product decision is asserted as a literal, not recomputed by the code that makes it; a grep of the code's own source guards a name, not behavior; a run of zero tests is a failure, so the count is checked, not the exit code alone. Reading a manifest or config file to check it against another artifact is not a source grep — that file is the artifact under test.
- **Prove the fix fires** (`rules/verify-before-done.md` Scope of Proof). A bug fix or new guard shows its new test failing with the fix reverted, then passing restored. A test written alongside a fix often passes on the old code too. PRs #20 and #24 already did this by hand; the rule makes it the expectation.

### Not changed

The audit after these edits found the Python suites already honour the zero-test bullet — `unittest.main` exits 5 on "NO TESTS RAN" and `scripts/run-tests.sh` counts it as a failure — but the shell harnesses each print their own summary and exit 0 on zero cases. Enforcing a count there needs a shared summary contract across every harness and is tracked separately.

- **Native Codex plugin packaging.** `.codex-plugin/plugin.json` exposes the existing four skills as `gamussa-coding-policy`, distinct from the Cyberdyne demo plugin named `coding-policy`. `hooks/hooks.json` registers the original SessionStart and Stop hooks. The SessionStart adapter reads the Tessl manifest's rule list, identifies always-on and conditional rules for the agent to read, maps co-shipped Tessl script references to the installed Codex root, and translates portable hook output to Codex's native context envelope. The rule bodies, skill files, and existing hook scripts stay shared across both installation paths.
- **Codex installation and verification instructions.** Personal marketplace entries are appended without replacing existing entries; hooks require the host's trust review and a new thread. Herdr's policy resolver falls back to the native Codex index and release skill when Tessl artifacts are absent, preserving local-then-global Tessl precedence. The boundary tests cover installed paths with spaces, rule scopes, invalid input, missing files, path containment, context translation, child failures and timeouts, and agreement between the two manifests and hook registrations. Codex and Tessl versions advance together.

### Fixed

- **Codex hook timeouts terminate the process group.** Killing only the immediate Bash wrapper left foreground `tessl` or `git` descendants running after a reported timeout. The adapter now starts each translated hook in a separate POSIX session and kills the group before draining output. A real-descendant pipe test checks that timeout cleanup releases inherited output streams.
- **The test runner's empty-tree error on macOS Bash 3.2.** Nested command-substitution quoting expanded the `{sh,py}` suffix into two arguments and emitted two JSON objects. Building the error message before escaping keeps the promised single JSON result; the existing empty-tree test covers it.

## 0.4.0 — 2026-09-17

### Added

- **`rules/cross-boundary-changes.md`.** A change that touches a shared contract is mapped before it is edited: the producer, each consumer, the contract, and the verification command per boundary, stated in a few lines before the first edit. Compatibility is resolved explicitly, with a staged migration preferred when consumers deploy separately; conflicting instruction files are cited on both sides rather than silently resolved; one coherent change at a time, narrow tests first, every unverified boundary reported with its consequence. Ported from the `multi-module-changes` skill in [cyberdyne-systemz/coding-policy](https://github.com/cyberdyne-systemz/coding-policy), Viktor's own smaller Codex-plugin policy, which had the one idea this plugin lacked.
- **PR body: Change / Verification / Policy and risks.** The release skill's Step 2 template replaces Summary plus a Test-plan checklist with the three sections the cyberdyne `pr-template.md` carries: the concrete trigger and before/after behavior; each exact command with its observed result and every check not run named as such; the rule names, compatibility impact, and remaining limits. A repo's own `.github/pull_request_template.md` still wins.
- **Provenance honesty in `rules/verify-before-done.md`.** Never invent a PR URL, CI result, run id, or registry state; a local draft is never "the PR" and a prepared fixture is labelled prepared; an approval, auth, or network failure is reported as that failure, never as a policy rejection. From the cyberdyne `prepare-pr` skill and workflow policy.
- **Stage only the intended files.** `rules/commit-conventions.md` One Change Per Commit now says it at the staging step: inspect `git status` first, and unrelated uncommitted work stays out of the commit.

Not ported from the same repo: the read-only MCP policy server and the Codex manifest (Tessl already installs the rules into every agent's context, Codex included), the prepare-only draft mode (it contradicts `rules/ship-on-green.md`), and the hooks-guide-while-branch-protection-enforces disclaimer (the release contract already treats CI and the reviewer verdict as the gate).

## 0.3.0 — 2026-09-15

### Added

- **Herdr fleet synced to upstream 0.3.232.** Twenty-seven upstream releases in five days, taken wholesale into `skills/herdr-teamlead`, `skills/herdr-standup`, `rules/agent-team-operation.md`, and the Herdr hooks, with our five local reconciliations re-applied on top (report-file Phase 2 reviews, the release worker's worktree-only Step 7, no AI disclosure in briefs, full reference paths, and the standup prose trims). What arrived, in the order upstream shipped it: an on-demand specialist bench (UX/product, accessibility, investigator, architect, security, performance/reliability, documentation) with capability and contribution based staffing; a planner that refuses a field it could not have ranked; an open decision or blocker on a task that stops further dispatch on that task; provider refusals recorded, moved once unchanged, then stopped; `prune-worktrees.sh` run before provisioning and after the merge; an exhausted fix allowance that goes to the investigator and then to the judge in a second, diagnosis mode returning `DIAGNOSIS` / `REMEDY: continue | restructure | stop` / `BOUND` / `ASSESSMENT` / `EVIDENCE` / `UNVERIFIED`, with a remedy ladder that only descends; five composition triggers detected mechanically by `teamlead detect-triggers` from the round's diff against `.herdr/triggers.json`; a stall outcome in `wait-report.sh` (report absent, status terminal, budget spent) with the stalled worktree classified as evidence; review partitions validated by `teamlead validate-partition`; a task-owned fixture root carve-out; judge dispatches that declare adjudication or diagnosis mode; and the ledger and recovery fixes from #436 through #442.
- **This repo's trigger declaration.** `.herdr/triggers.json` names the package roots, trust boundaries (workflows, hooks, rules, the Herdr scripts and Python, the reviewer templates, the release scripts), CLI surfaces, and user docs the detector classifies a round against. It is `.tesslignore`d: consumers write their own.
- **`review_unrequested` in the pre-merge watch.** `poll-pr-reviews.sh` reports `requested` per reviewer lane from GraphQL (the REST endpoint omits bot reviewers), and `watch-pr-reviews.sh` ends at once with `review_unrequested` when Copilot has no verdict at the head and no pending request, naming the request command instead of spending its budget. `rules/ci-safety.md` Always Watch CI now separates the merge decision's blocking watch from a non-merging stage's single snapshot, and resolves a reviewer's arrival by how it is triggered. From upstream #369.
- **Judge-Accepted Defect Carve-Out in `rules/review-severity.md`.** A `stop` diagnosis may ship the clean scope with the remaining blocking finding recorded as a tracked accepted defect, every other gate held. From upstream #407.
- **`scripts/tests/test_source_index.py`.** The manifest's `rules` array, the maintainer index's `@`-imports, and `rules/*.md` on disk must agree, and every tracked Python file must sit under a pyright include. Adapted from upstream #368 to accept directory includes, which this repo uses.

### Fixed

- **Two untracked-file blind spots in the synced upstream code.** The handoff hook's cleanliness reads ran `git status --porcelain` without `--untracked-files=all`, so a checkout configured with `status.showUntrackedFiles=no` could read a worktree holding untracked work as clean and list it for removal; every cleanliness read now passes the flag, as `prune-worktrees.sh` already did. `teamlead validate-partition` without `--head` read `git diff` alone, which excludes untracked files, so a partition could pass while a new file sat unowned; the working-tree path now folds `git ls-files --others --exclude-standard` into the changed set, as trigger detection does. Both caught by the policy review on #4 and worth offering upstream.
- **`prune-worktrees.sh` re-reads the tip before removing a worktree.** A commit landing after the ancestry check left a now-unmerged checkout to `git worktree remove`; the compare-and-delete protected only the branch. The tip is re-read immediately before the removal and a moved branch keeps its worktree with reason `moved`, judged again on the next run. From the policy review on #4.
- **A stalled worker's older unpushed history is not its work.** `wait-report.sh --worktree` classified a clean checkout as `unpushed_commits` whenever any unpushed commit existed, including commits that predate the recorded dispatch base, so an untouched assignment was routed into completed-work recovery instead of the retryable `no_work` Stalled Workers prescribes. With a base, the dispatch's own range decides first, and unpushed evidence is scoped to it (`dispatch_unpushed_commits`); without a base the classifier reads as before. From the policy review on #4.
- **A developer's specialty no longer covers a fired trigger.** `teamlead detect-triggers` read the specialty of every planned assignment as consultation coverage, so a developer seated with `specialty: security` marked a fired security trigger addressed with no consultation and no staffing decision. Coverage now counts the advisor, investigator and architect seats alone. The round-flow re-entry text also routes a spent remedy through Step 12's exhaustion workflow, a fresh checkpoint and investigator assessment after the latest attempt, before the next diagnosis, as Fix Loops requires. Both from the policy review on #4.
- **Fixture-root carve-out rationale moved here.** `rules/agent-team-operation.md` Writers and Checkouts states the fixture-root exception's applicability condition without its rationale: a tool that resolves its configuration from filesystem ancestors, given a fixture under the home-based reports directory, walks up to the operator's own project file and initializes that project instead of the fixture's, which is what happened upstream in #367.
- **The handoff hook judges containment against fully qualified refs.** With short names, a tag named like the worker's branch won the resolution and read as zero commits ahead of the default branch, listing an unmerged checkout for removal; a local ref named `origin/main` could shadow the default the same way. The hook now resolves `refs/remotes/origin/<default>` and `refs/heads/<branch>` in full. From the policy review on #4.
- **The handoff hook sees every spent worktree.** A worktree that is clean and holds nothing the default branch lacks is reported removable whether or not its branch was ever pushed; dirty, unmerged, locked, and detached worktrees reach the operator on stderr with their reason and are never listed for removal. The supervision Stop hook no longer writes bytecode into the installed plugin. From upstream #433 and #385.

## 0.2.0 — 2026-09-09

### Added

- **The Herdr fleet, ported wholesale from upstream 0.3.205.** `skills/herdr-teamlead`, `skills/herdr-standup`, `rules/agent-team-operation.md`, `rules/stateful-artifacts.md`, and the `herdr-team-status` (SessionStart) and `herdr-supervision-stop` (Stop) hooks arrive as Baruch shipped them on 2026-09-09, re-namespaced to the `gamussa/coding-policy` mount path. This is the whole protocol he built over four days and sixteen releases: three rotating roles plus a pinned judge, headroom-driven assignment, reports as files with the `REPORT: <path>` marker, internal reviewer and tester passes on the pushed SHA before the PR opens, a five-round fix allowance with retained context for rounds 1 to 3 and a fresh worker after, the judge's `RULING` / `ACTION` / `UNVERIFIED` deliverable, a lead-owned task ledger that separates delivered reports from accepted work and completed tasks, a persistent attention queue, daily and pre-transition retrospectives, lead handoff stows, fleet supervision with an exact-session Stop gate, and verified YOLO relaunches with tier qualification. The 0.1.0 decision to leave this layer out is reversed on the strength of that protocol; the Python under `skills/herdr-teamlead/teamlead/` and its 40-odd suites come along because the protocol is only enforceable through them. Standalone sessions (no `HERDR_ENV`) are untouched: the rule's first section says none of it applies there.
- **GitHub tag/asset publication verification.** `skills/release/verify-github-release.sh` confirms a tag-triggered release the way `verify-publish-landed.sh` confirms a Tessl publish: the resolved run concluded `success` AND a published, non-draft release exists at the exact tag with every asset retrievable. `resolve-publish-run.sh` takes an optional fifth `ref` argument so a tag run, whose `headBranch` is the tag name, resolves through the same four-fact binding. `rules/ci-safety.md` Always Watch CI and the release skill's Steps 3 and 7 now key the confirmation on the publication, not the package: a repo that publishes on both channels owes both confirmations, and neither substitutes for the other. Motivated by upstream #371/#374, where a main-only lookup missed a tag run and a Tessl-only confirmation was applied to a repo that no longer published through Tessl.
- **Imported-tree carve-out in `rules/language-diagnostics.md`.** The port brings the first Python into this repo, and pyright's strict mode reports 16,102 findings on it while standard reports zero. Adopting on a Dirty Tree now says explicitly how a tree the project's configured level has never checked enters the gate: at the engine's default level with zero findings, no rule switched off, no file excluded, the strict-level count recorded in the importing PR, and the adoption filed as an issue (#2) that follows the existing config / fix / CI-gate sequence. Every other lowering of a configured level stays blanket silencing. Raised by the policy review on #1, which read the config diff as a repository-wide suppression.
- **Herdr bootstrap carve-out in `rules/script-delegation.md`.** The Herdr skills' command blocks open with a two-line `CP` resolver (project-local plugin, then `$HOME`) before invoking a co-shipped script. That inline branch is the one sanctioned exception to Scripts Are Real Files, bounded by five preconditions and checked by `skills/herdr-teamlead/tests/test_skill_invocations.sh`.

### Fixed

- **`stop-handoff-hygiene` on stock macOS Bash 3.2 and inside Python projects.** Empty-array expansions under `set -u` no longer abort the hook when the repo has no gone branches or linked worktrees. Pyright now runs with the project's own interpreter (`VIRTUAL_ENV`, then `.venv`, then `venv`) and prefers that environment's pyright, so a changed file's imports resolve against the project's dependencies instead of a global engine; nested worktree calls resolve from the repository root. Findings, including missing imports, stay blocking. Both from upstream #351.
- **Two contradictions in the upstream Herdr briefs.** The reviewer brief's Mode B told the worker to post a GitHub COMMENT review on a PR that, by the Review Before PR sequence, does not exist yet; the report file is now the Phase 2 review, and the COMMENT form applies only when a PR already exists for the branch. The release brief sent the worker through the release skill's Step 7 unadapted, including the base-checkout fast-forward and `git worktree remove` that Writers and Checkouts forbids a worker to run; the brief now runs the merge and publication verification from the worktree and leaves the local cleanup to the lead. `rules/agent-team-operation.md` Review Before PR, `COMMON.md`, and `round-flow.md` say the same thing. ## 0.1.0 — 2026-09-07

### Added

- **Initial release.** A fork-in-spirit of [jbaruch/coding-policy](https://github.com/jbaruch/coding-policy), rebuilt for Viktor Gamov's agents. The language-agnostic code rules, the autonomous-shipping discipline, the session hooks, the Codex policy reviewer, and the release skill are ported; the Herdr multi-agent layer, the fleet reviewer App, the auto-bump publish pipeline, and the skill-review gate are not.
- **24 rules.** Ten code-quality rules (commits, sync-before-work, testing, error handling, dependencies, file hygiene, CI safety, secrets, formatting, language diagnostics), eleven agent-behavior rules (boy-scout, ship-on-green, response-clarity, worktree isolation, review severity, reviewer-feedback reading, external-repo default-deny, hook-action reporting, verify-before-done, environment-changes, demo-readiness), and three plugin-authoring rules (script delegation, skill authoring, context artifacts).
- **Stack defaults.** `testing-standards`, `code-formatting`, and `language-diagnostics` name the tools to reach for on JVM (Kotlin/Java), Swift, TypeScript, and Python projects that have none configured. An existing project's configured tool always wins.
- **Three new rules Baruch's set does not carry.** `verify-before-done`: "done" means a shown passing run, never "should work". `environment-changes`: no machine-level installs or new project dependencies without stating them first; CI-runner installs are exempt. `demo-readiness`: conference-talk and workshop repos run top to bottom from a fresh clone with one command, a documented reset, and an offline-capable default path. `commit-conventions` additionally forbids AI attribution trailers in commits and PRs.
- **Manual versioning instead of auto-bump.** Every PR that changes shipped content bumps the manifest version and writes the CHANGELOG heading itself; `scripts/check-version-bump.sh` fails the PR when the manifest is not ahead of the registry or the heading is missing. `publish.yml` publishes the manifest version as-is on merge. This trades Baruch's registry-aware auto-bump plus stamp step for one deterministic gate and no bot commits on `main`.
- **Hooks.** `check-git-sync`, `check-policy-freshness`, and `check-tessl-latest` at `SessionStart` (informative, `Session-start status — ` marker); `stop-handoff-hygiene` at `Stop` for Claude Code and Codex (blocks once on leftover merged branches, orphaned worktrees, or diagnostics findings in the changed set).
- **Skills.** `release` (PR, Codex policy review plus advisory Copilot, watch, merge, cleanup, publish confirmation) and `onboard-repo` (install the plugin at `latest`, scaffold the per-repo Codex reviewer workflow that reads rules from a checkout of this repo, set the `CODEX_AUTH_JSON` secret, open the PR).
